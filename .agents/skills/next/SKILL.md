# /next - 下一步建议

作为项目开发顾问，综合分析项目全貌后，推荐**一个最优下一步**和备选方向。只读，不修改任何文件。

---

## 第一步：收集项目全貌（6 个数据源，并行执行）

### 1.1 Git 提交分析（按进度口径分类）

```bash
git log -15 --format="%H|%an|%cn|%s" --no-merges
```

口径与 `CLAUDE.md`「提交与进度口径」一致（`.claude/framework-config.json` 的 `progress`）：

| 分类 | 识别方式 | 用途 |
|------|---------|------|
| 业务进度提交 | 类型为 `feat` / `fix`，且 scope 不是 `framework` / `strip` / `data` / `deps` | 判断「最近在做什么」 |
| 框架与维护提交 | 其余类型与排除的 scope（`docs(tasks)`、`chore(data)`、`refactor(strip)`…） | 只作背景 |
| 同步提交 | message 含 `cherry picked from`，或以 `chore(framework-sync)` 开头，或 author ≠ committer | 单独标注，不作方向判断 |

**输出**：业务进度提交列表、同步提交列表（单独标注）、最近开发方向（按 scope 归类，如 `videos`、`seo`、`series`）。

### 1.2 任务台账（最重要的数据源）

```bash
grep -rnE "^- \[ \] T[0-9]+" docs/tasks/active/ 2>/dev/null    # 未完成的任务行
```

🔴 只有「## 🎯 实现步骤」区块里以 `- [ ] T<数字>` 开头的行才是任务；待决策事项等其他复选框不算任务（但「待决策事项」要作为需要用户拍板的问题提出）。

对每个台账，**深度读取**：

| 读取区域 | 提取信息 | 用途 |
|---------|---------|------|
| 文件头部 | 状态（进行中 / 暂停）、更新时间 | 判断是否停滞 |
| 任务行 + 字段 | 按编号第一个未勾、且 `依赖:` 都已完成的 `T<数字>`；它的 `需求:`、`读写:`、`里程碑:`、`文件:` | 确定下一步 |
| 当前进度 | 「正在进行」「下一步操作」「阻塞问题」 | **直接作为推荐依据** |
| 问题记录 | 🔴 待解决 / 🟡 进行中 的问题 | 判断阻塞 |

- 有阻塞问题 → 推荐解决阻塞
- 下一个可做的 `T<数字>` 明确 → **直接推荐它**（入口 `/dev-loop T<编号>`）
- 超过 7 天未更新 → 提醒是否继续或暂停

### 1.3 待办清单

读取 `docs/待办清单.md`：高 / 中 / 低优先级数量与内容、逾期项。

### 1.4 需求文档

读取 `docs/需求文档.md`：状态为「待开发」「开发中」的 REQ 及优先级。

### 1.5 站点健康信号

```bash
ls dist/index.html 2>/dev/null && pnpm check:seo    # 已有构建产物时读取 SEO 校验结果（不重新构建）
grep -nE "^- \[ \] \[(需决策|可逆)\]" docs/BLOCKERS.md 2>/dev/null   # 自主循环留下的未处理项（格式见 CLAUDE.md「阻塞记录」）
grep -n "example.com" src/site.config.ts              # 域名是否仍是占位
```

- `check:seo` 有错误 → 属阻塞性问题
- `docs/BLOCKERS.md` 有未勾的 `[需决策]` 行 → 需要用户决策，优先提出；未勾的 `[可逆]` 行 → 提醒用户复核循环采用的默认做法
- 仍是占位域名且需求里有上线目标 → 提醒上线前必须改

### 1.6 代码待办扫描

```
Grep pattern: "FIXME" path: src glob: "*.{astro,ts,tsx}" output_mode: content -i
Grep pattern: "TODO" path: src glob: "*.{astro,ts,tsx}" output_mode: count
Grep pattern: "FIXME|TODO" path: scripts glob: "*.mjs" output_mode: count
```

> docs/ 下的某个文档不存在 → 跳过该数据源，不报错、不自动创建。

## 第二步：智能分析与排序

### 2.1 判断当前上下文

| 信号 | 判断 |
|------|------|
| 有活跃任务且未完成 | **优先继续未完成任务** |
| 最近提交集中在某个 scope | 建议在同一块继续延伸 |
| `check:seo` 报错 / 构建失败 | 优先修复 |
| 待办清单有高优先级 | 优先推荐高优先级待办 |
| 需求文档有「开发中」需求 | 优先完成进行中的需求 |
| 需求全部完成但未验收 | 推荐 `/seo-check` → `/deploy` |

### 2.2 优先级排序

```
1. 🔴 活跃任务的阻塞问题 / docs/BLOCKERS.md 的 [需决策] 项
2. 🟠 台账里下一个可做的 T 任务（已明确跟踪的工作，有完整上下文）
3. 🟡 阻塞性问题：构建失败、check:seo 错误、FIXME
4. 🟢 高优先级待办
5. 🔵 需求文档中「待开发」的需求（按优先级）
6. ⚪ 代码 TODO、低优先级待办、SEO 警告
```

**核心理念**：活跃任务代表已投入的进行中工作，中断后恢复的成本远高于开新任务，除非有紧急阻塞，否则**始终优先推荐继续活跃任务**。

### 2.3 连贯性

- 最近在做内容类型 A（如 videos 列表页）→ 优先推荐 A 的下一步（详情页 / 分类页 / 数据源）
- 最近在修 SEO 问题 → 优先推荐同类问题
- 一个内容类型刚做完 → 自然延伸：接入 llms.txt 与导航 → 首页露出 → `/seo-check`

## 强制规则

| 规则 | 说明 |
|------|------|
| 不预估时间 | 禁止输出「预计 X 小时 / 天」 |
| 不给空泛建议 | 每条具体到路由 / 文件 / 操作 |
| 按进度口径看提交 | 只用业务进度提交判断方向；同步提交不作为方向判断 |
| 读取任务和待办 | 必须尝试读取 `docs/tasks/active/`（只认 `T<数字>` 任务行）与 `docs/待办清单.md` |
| 一个推荐 + 备选 | 推荐区只放一个最优建议 |
| 连贯性优先 | 未完成任务 > 新任务，同一内容类型 > 跨类型 |
| 文档不存在时跳过 | 不报错、不创建 |
| 标注来源 | 每条建议标注数据来源 |
| 只读 | 不修改任何文件 |

## 与其他命令的关系

| 命令 | 关系 |
|------|------|
| `/progress` | 全面进度报告（只读），/next 是精简的下一步建议 |
| `/update-status` | 更新文档，/next 只读取 |
| `/add-todo` | 添加待办，/next 从待办中读取推荐 |
| `/dev` `/collection` | 开始开发，/next 告诉你该开发什么 |
