# 头脑风暴框架

## 何时使用

- 不知道页面或栏目该怎么设计
- 需要多种方案对比后再定方向
- 新增一类内容（视频、项目、产品、案例…）不知道怎么组织
- 功能规划、站点信息架构讨论
- 静态站想加动态能力（评论、表单、实时数据）不知道怎么做
- 业务扩展：一个站点要承载新目标

其他常见说法：方案、怎么设计、讨论、想法、建议、有哪些方式、能不能做、可以实现吗。

## 本项目技术约束（头脑风暴边界）

> **重要**：所有方案必须在以下技术栈约束内思考。突破边界的方案要单独标注「需要 tech-decision 评估」。

### 已有能力

| 层面 | 已有能力 | 位置 |
|------|---------|------|
| **框架** | Astro 7（纯静态输出）+ Vite 8 | `astro.config.ts` |
| **样式** | Tailwind CSS v4 + 语义设计令牌 + 深色模式 | `src/styles/global.css` |
| **交互** | React 19 island（只在需要状态的区块水合） | `src/components/islands/` |
| **数据** | 内容集合：`categories` / `works`（JSON）/ `posts`（Markdown） | `src/content.config.ts` |
| **外部数据** | 构建前数据同步（失败保留旧数据、骤降保护、原子写入） | `scripts/sync/` |
| **检索** | 前端子串匹配（中文友好，零依赖） | `src/lib/search.ts` |
| **SEO/GEO** | 逐页 canonical / OG / JSON-LD、robots 放行 AI 爬虫、llms.txt、sitemap | `SEOHead.astro`、`src/pages/*.txt.ts` |
| **图片** | 构建期远程图片转存 + WebP + srcset | `src/lib/images.ts` |
| **过渡动效** | CSS 跨文档视图过渡（零 JS） | `global.css` |
| **部署** | Docker 多阶段构建 + nginx 静态托管 | `Dockerfile`、`deploy/nginx/` |

### 默认不在范围内（出现就要单独评估）

| 能力 | 为什么不默认提供 | 需要时的方向 |
|------|----------------|-------------|
| 服务端渲染 / API 路由 | 纯静态站没有运行时服务器，部署与运维成本最低 | 先想「构建期能不能算好」；确实需要走 `tech-decision` |
| 用户登录 / 会员 | 静态站没有会话 | 第三方服务或另起后端 |
| 数据库 | 内容集合就是数据层 | 构建期从数据库导出 JSON |
| 评论 / 点赞 | 需要写入能力 | 第三方评论服务（见 `tech-decision`） |
| 实时数据（在线人数、实时播放量） | 静态页只在构建时刻准确 | 定时重建，或 island 在浏览器里调公开接口 |
| 中文 webfont | 体积大、伤首屏 | 系统字体栈 |

## 头脑风暴交互纪律（分段确认 · 必须遵守）

> **纪律：不要一次性吐出完整方案**。按段提问、逐段确认，让用户在每一步把关，避免「方向跑偏到最后才发现」。

### 分段推进（每段确认后再进下一段）

| 段 | 你做什么 | 闸门 |
|----|---------|------|
| ① 澄清问题 | 用 1-3 个关键问题问清「给谁看、看完要他做什么、内容从哪来」（参考下方「讨论引导问题」），**一次别问太多** | 用户答完才进 ② |
| ② 资源盘点 | 列可复用的集合 / 组件 / 页面模式，指出哪些要新开发 | 用户认可才进 ③ |
| ③ 方案对比 | 给 2-3 个方案 + 评分矩阵，**逐个讲、不要堆** | 用户选定方向才进 ④ |
| ④ 推荐定稿 | 按选定方向给推荐方案 + 实施步骤 + 风险 | 用户点头才保存结论 |

### 纪律要点
- **一段一确认**：每段结束明确问「这段 OK 吗 / 选哪个 / 要改吗」，得到回应再继续。
- **不臆造**：信息不足先问，别替用户假设内容量、受众、数据来源；不编造流量数字与竞品数据。
- **可降级**：用户说「别问了，直接给方案」时，可一次性输出，但仍保留分段结构便于回看。

## 思维模式

### 发散思维 - 尽可能多的方案

1. **不评判**：先不考虑可行性，尽可能多地列出想法
2. **联想**：从一个想法延伸到相关想法（一个「作品列表」可以延伸出系列、时间线、专题、学习路径）
3. **复用优先**：现有的 `works` / `categories` / `posts` 三种集合形态能不能直接套用？
4. **跨界借鉴**：同类优秀站点怎么组织内容（按主题？按时间？按难度？）
5. **反向思考**：怎样让访客最找不到想要的内容？反过来就是信息架构的答案

### 收敛思维 - 筛选最优方案

1. **构建期优先**：能在构建时算好的，就不放到浏览器里算
2. **零 JS 优先**：能用 `.astro` + CSS 做的，就不做 island
3. **可收录**：每个值得被搜到的内容都有独立 URL
4. **数据可维护**：谁来更新内容？手工还是同步？更新频率多高？
5. **成本**：开发量、依赖数量、部署复杂度
6. **风险**：外部接口会不会限流 / 下线？数据缺失时页面会怎样？

## 本项目专属决策维度

### 必须考虑的 5 个维度

| 维度 | 关键问题 | 影响 |
|------|---------|------|
| **渲染时机** | 这个数据在构建期能确定吗？ | 能 → 静态；不能 → island 客户端取数或定时重建 |
| **URL 与收录** | 这类内容需要被搜索引擎 / AI 单独引用吗？ | 需要 → 独立详情页 + 分类落地页 + JSON-LD |
| **数据来源** | 手工维护、外部接口、还是 Markdown 写作？ | 决定用 `file()` 还是 `glob()` loader，要不要写同步源 |
| **JS 预算** | 这个交互值多少 KB？ | React 运行时只加载在有 island 的页面上 |
| **国内访问** | 访客主要在国内吗？ | 决定托管平台、是否需要备案、第三方脚本能否访问 |

### 方案评估矩阵（本项目版）

| 方案 | 复用度(25%) | 可收录(25%) | JS 成本(20%) | 维护成本(15%) | 开发量(15%) | 总分 |
|------|-----------|-----------|------------|-------------|-----------|------|
| A | | | | | | |
| B | | | | | | |

**评分说明**（每项 1-5 分）：
- 复用度：能多大程度套用现有集合、组件、页面模式
- 可收录：内容是否有稳定 URL、是否能输出完整 SEO 字段
- JS 成本：分越高 = JS 越少（零 JS 5 分，整页 island 1 分）
- 维护成本：分越高 = 日常更新越省事
- 开发量：分越高 = 工作量越小

## 本项目典型业务场景

### 场景 1：新增一类内容（如「视频合集」「开源项目」）

```
需求：站点要展示一类新内容
│
├── 先问：它和 works 的区别在哪？
│   ├── 只是换个名字 → 直接用 works，改文案
│   └── 字段 / 页面形态不同 → 新集合（/collection 命令）
│
├── 组织方式
│   ├── 按分类（categories 引用）
│   ├── 按系列（有顺序，像课程目录）
│   └── 按时间线
│
└── 页面
    ├── 列表（要筛选 → island；不要 → 静态）
    ├── 详情（每条一个 URL）
    └── 分类 / 系列落地页（长尾关键词承接）
```

### 场景 2：接入外部数据源（B 站、GitHub、RSS…）

```
需求：内容来自外部平台，要自动更新
│
├── 拉取时机
│   ├── 构建前同步（推荐）→ scripts/sync/sources/<name>.mjs
│   └── 浏览器实时拉（只适合展示实时数字，且不利于收录）
│
├── 风险
│   ├── 接口签名 / 风控 → data-sync 技能的防风控章节
│   ├── 接口失败 → 运行器保留上一版数据
│   └── 图片防盗链 → 域名加入 site.imageDomains 构建期转存
│
└── 更新频率
    ├── 手动 pnpm sync 后提交
    └── 定时任务（本机 / 国内服务器）同步 + 重建
```

### 场景 3：站内搜索

```
需求：访客要能搜到内容
│
├── 只搜标题 / 摘要 / 标签（几百到几千条）
│   └── src/lib/search.ts 子串匹配 ✅ 首选
│
├── 要搜文章全文
│   └── Pagefind 构建期索引
│
└── 数据量极大 / 要拼写纠错 / 要统计
    └── 第三方搜索服务（成本与国内可用性要评估）
```

### 场景 4：静态站要「动」起来（评论、点赞、表单、订阅）

```
需求：访客要能留下点什么
│
├── 评论 → 第三方评论服务（tech-decision 选型）
├── 联系表单 → 表单服务 / 邮件链接 / 企业微信群二维码
├── 订阅 → RSS（零成本）/ 邮件订阅服务
└── 原则：写入能力交给第三方或独立后端，站点本身保持纯静态
```

### 场景 5：多语言

```
需求：要做英文版
│
├── 是否每页都要翻译？
│   ├── 是 → Astro i18n 路由（i18n-development）
│   └── 否 → 只做英文落地页 + hreflang
│
└── 内容维护：翻译谁来做？同步更新怎么保证？（先问清再动手）
```

### 场景 6：让 AI 搜索引用本站

```
需求：希望 ChatGPT / Perplexity 等能引用
│
├── 站内写法：首段定义句、短段落、表格列表、数据带出处
├── 结构化：FAQPage / Article / BreadcrumbList
├── 可发现：robots 放行 AI 爬虫、llms.txt、sitemap 提交 Bing
└── 走 geo-optimization 技能落地
```

## 创意激发技巧（本项目版）

### 1. 集合组合法

同一份数据换一种组织方式，就是一个新页面：

```
works
├── 按分类 → 分类落地页
├── 按标签 → 标签聚合页
├── 按时间 → 年度归档 / 时间线
├── 按热度 → 精选 / 排行
└── 按顺序 → 系列 / 学习路径
```

### 2. 访客任务法

从「访客来站点要完成什么任务」倒推页面：找某一条 → 搜索；随便逛逛 → 精选与分类；系统学习 → 系列路径；判断可不可信 → 关于页与数据来源说明。

### 3. 零 JS 思考法

每想到一个交互，先问「CSS 或 HTML 原生元素能不能做」：折叠用 `<details>`、切换用 `:target` / `:has()`、过渡用 View Transitions、筛选结果页用静态分类页代替。

### 4. 收录反推法

先想「用户会在搜索框里输入什么」，每个值得被搜到的词都应该有一个页面承接（分类页、专题页、FAQ）。

### 5. 联网借鉴法（按需触发，不是默认动作）

何时**该**联网查：
- 涉及新技术 / 新版本，训练数据可能过时（Astro 7 相关尤其如此）
- 用户明确说「业界怎么做」「看看同类站点」「参考官方文档」
- 准备给出技术选型，但对该领域的最新做法没把握

何时**不该**联网：
- 框架内已有模式能直接套用
- 已经有明确方向，只是要细化

> 工具选择：主流库官方文档 → `context7`（Astro 查 `/withastro/docs`）；业界案例 → WebSearch；JS 渲染的页面 → 智码内置浏览器。

## 讨论引导问题（本项目版）

### 功能规划时

1. 这个页面 / 栏目的**访客是谁**？他们从哪里来（搜索、社交平台、直接访问）？
2. 访客看完后，**希望他做什么**？（点进原平台、看下一条、联系、订阅）
3. 内容**有多少条**？一年后大概多少条？
4. 内容**谁来更新**？多久更新一次？
5. 哪些内容**值得被搜索引擎单独收录**？
6. 有没有**必须实时**的数据？能不能接受「构建时刻的快照」？

### 方案选择时

1. 这个方案**新增了多少 JS**？只在需要的页面加载吗？
2. 数据源挂了，**页面会变成什么样**？
3. 需要引入新依赖吗？有没有**国内访问**问题？
4. 半年后换一个人维护，**看得懂吗**？

### 头脑风暴结论保存（必须执行）

头脑风暴完成后，**必须**将结论保存为文档，方便后续跨会话查看和更新。

**保存路径**：`docs/brainstorm-{主题简称}.md`（主题简称用中文，如 `brainstorm-视频合集.md`）

> 在框架模板里走 `/kickoff` 阶段一时，这份文档先落在框架的 `docs/` 下；`project-init` 孵化时会把它连同需求文档、原型一起带进新项目，并（经用户同意）从框架目录清理掉。

```markdown

**创建时间**: YYYY-MM-DD HH:MM
**最后更新**: YYYY-MM-DD HH:MM
```

## HTML 原型生成（UI 类需求 · 优先工作站，禁手搓）

方案确定后，**若涉及页面 UI**，优先用可视化原型代替纯文字描述，让用户「看着确认」。

### 必须遵守
- 🔴 **禁止手搓 HTML 充当原型**。一律走 **AI 工作站 ui-studio**：
  `ai-workstation MCP → route(query=按需求做 xxx 页面的 UI 原型) → get_skill(projectId=ai-ui-studio, skillName=<route 命中的技能>)` → 按技能执行 → 产出到 `docs/prototypes/<业务>/*.html`。
  工作站 MCP 调不通时停下告知用户，不降级成手写原型。
- 原型 HTML 带「组件映射表」注释：原型里的区块对应框架的 `Container` / `Section` / `Button` / `Badge` / `Breadcrumbs` / `WorkCard`，颜色对应语义令牌（`bg-canvas`、`text-ink`、`text-muted`、`border-line`、`text-brand-ink`），便于后续 `html-to-code` 转码 + `dev-loop` 截图逐元素对照。
- **纯数据 / 无界面需求 → 跳过本步**，别画蛇添足。

### 与下游衔接
- 原型 → `writing-plans` 把 UI 任务写成「`html-to-code` 转码 + e2e 截图对照原型」。
- 原型缺失但有 UI 任务时，`writing-plans` / `dev-loop` 会回标「先补原型」，**不自行手搓**。

### 保存后的下一步建议

```markdown
💡 **下一步建议**：

1. **（UI 类）先出原型** → 工作站 ui-studio 产 `docs/prototypes/<业务>/*.html`
2. **拆可执行计划** → 激活 `writing-plans`，把方案落成 `docs/tasks/active/` 细颗粒计划
3. **自主执行** → `/loop /dev-loop`
4. （轻量）**初始化项目文档** → `/init-docs {功能描述}`；**直接开发** → `/dev`
```

## 常见问题快速决策

| 问题 | 推荐方案 | 原因 |
|------|---------|------|
| 新内容用 works 还是新集合？ | 字段和页面形态一致就复用 works | 少一套页面与查询要维护 |
| 列表要不要做 island 筛选？ | 条目 > 20 且有多个维度时做 | 少量内容用静态分类页更轻 |
| 实时数字（播放量）怎么显示？ | 构建期快照 + 标注「截至某日」 | 静态站的数字只在构建时刻准确 |
| 搜索用什么？ | `src/lib/search.ts`，要搜全文再上 Pagefind | 中文子串匹配零依赖且准确 |
| 要不要评论？ | 先问目的，确需再选第三方 | 写入能力会破坏纯静态的简单性 |
| 图片放哪？ | 外部平台封面走构建期转存 | 防盗链、可控、能出 WebP |
| 要不要英文版？ | 先确认翻译来源与维护人 | 没人维护的双语站比单语站更伤 |

## 🔗 关联技能边界

本技能专注于**开放式方案探索**（还不知道怎么做时）。遇到以下场景请改用其他技能：

| 场景 | 应使用技能 | 判断关键词 |
|------|-----------|-----------|
| 方向已定、要设计栏目与 URL 结构 | `architecture-design` | 「信息架构」「URL 结构」「栏目」 |
| 方向已定、要选 A 还是 B | `tech-decision` | 「Pagefind 还是子串匹配」「哪个好」 |
| 方案已定、要拆可执行计划 | `writing-plans` | 「写计划」「拆任务」「实施步骤」 |
| 已确定功能、要跟踪实施 | `task-tracker` | 「创建任务跟踪」「记录进度」 |

**三阶段辨别**：
1. **brainstorm** = 方案发散阶段（输出 2-3 个方向）
2. **architecture-design** = 结构落地阶段（选定方向后定栏目、URL、集合）
3. **tech-decision** = 决策收敛阶段（两个方案二选一）

**输出链路**：`brainstorm` 确定方案 →（UI 类经工作站出 `docs/prototypes/*.html`）→ `writing-plans` 拆计划入 `docs/tasks/active/` → `/dev-loop` 执行（里程碑 `/update-status` 聚合）。
